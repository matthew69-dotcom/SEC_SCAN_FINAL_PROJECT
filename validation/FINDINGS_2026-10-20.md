| หมวด | เครื่องมือ | วิธี | เกณฑ์ pass |
| :-- | :-- | :-- | :-- |
| TLS | Qualys SSL Labs **API v3** (`api.ssllabs.com/api/v3/analyze`, `fromCache=on&maxAge=24`, ไม่ publish) | อ่าน JSON ทีละโดเมน | `cert_valid`: ทุก endpoint ไม่ได้เกรด T **และ** leaf cert ยังไม่หมดอายุ · `hostname_match`: leaf cert ไม่มี issue bit 8 (hostname mismatch) · `modern_protocol`: รองรับ TLS 1.2 หรือ 1.3 |
| Headers | securityheaders.com (`?q=https://<domain>&followRedirects=on`) | อ่านตาราง *Raw Headers* ของ response สุดท้ายหลัง redirect แล้วตัดสินด้วย **เกณฑ์เดียวกับระบบเรา** (ดู `README.md`) | ตาม README; header ที่ส่งซ้ำ (เช่น `nosniff` 2 ครั้ง) นับตามความหมาย |

หมายเหตุ:
- API v3 ใช้ได้โดยไม่ต้องลงทะเบียน (v4 ที่ `validate.py --ssllabs-email` ใช้ ต้องลงทะเบียนด้วยอีเมลองค์กร)
- `example.com` — SSL Labs ปฏิเสธ (`Hostname blacklisted`) จึงไม่มี reference ด้าน TLS 3 แถว
- `tls.hostname_match` เดิมใช้เกณฑ์ "เกรด ≠ M" แต่เมื่อมีปัญหา trust ด้วย SSL Labs จะแสดงเกรด T ซึ่งบัง M
  (เคส `wrong.host.badssl.com`) จึงเปลี่ยนไปดู cert issue bit 8 แทน — แก้ใน `validate.py` ให้ตรงกันแล้ว
- แถว headers ของ badssl ทั้ง 3 โดเมนไม่ถูกนับ เพราะระบบเราไม่ได้ผล header (fetch ล้มเพราะใบรับรองเสีย
  ซึ่งถูกต้อง: client ปกติก็เปิดไม่ได้)

| # | โดเมน | Check | เรา | อ้างอิง | ประเภท | คำอธิบาย | สถานะ |
| --: | :-- | :-- | :-- | :-- | :-- | :-- | :-- |
| 1 | self-signed.badssl.com | tls.cert_valid | pass | fail | **(ก)** | เราตรวจแค่วันหมดอายุ ไม่ตรวจ trust chain (คาดไว้แล้วใน README) | **แก้แล้ว** — handshake ที่ 2 แบบ verify |
| 2 | thaigov.go.th | headers.nosniff | fail | pass | **(ก)** | เว็บส่ง `X-Content-Type-Options` **ซ้ำ 2 ครั้ง** → httpx รวมเป็น `"nosniff, nosniff"` → เราเทียบเท่ากับ `"nosniff"` ไม่ผ่าน | **แก้แล้ว** — แยกค่าด้วย comma |
| 3 | wrong.host.badssl.com | tls.cert_valid | pass | fail | (ข) | SSL Labs ได้ใบ *fallback* ของ badssl (`badssl-fallback-unknown-subdomain-or-no-sni`, หมดอายุ 2018) ส่วนเราได้ `*.badssl.com` ที่ยังไม่หมดอายุ → คนละใบกัน. ใบของเรา chain ถูกต้อง ปัญหาจริงคือชื่อไม่ตรง ซึ่ง `tls.hostname_match` ของเรา fail ถูกต้องแล้ว | อธิบายในเล่ม |
| 4 | google.com | headers.hsts | fail | pass | (ค) | ปลายทาง `www.google.com` ส่ง HSTS / Permissions-Policy ให้ securityheaders.com (สหรัฐฯ/ยุโรป) แต่ไม่ส่งให้เรา (ไทย, 14 ต.ค.) — Google ส่ง header ต่างกันตามภูมิภาค/ผู้ขอ | สแกนซ้ำให้ใกล้เวลากัน |
| 5 | google.com | headers.permissions_policy | fail | pass | (ค) | เหมือนข้อ 4 | 〃 |
| 6 | youtube.com | headers.csp | pass | fail | (ค) | securityheaders.com ได้ CSP **3 header** (รวม `'unsafe-inline'` 2 ครั้ง) แต่ evidence ของเราเห็น CSP 1 header (`'unsafe-inline'` 1 ครั้ง) — YouTube ส่ง policy ต่างกันตามผู้ขอ | 〃 |
| 7 | wikipedia.org | headers.hsts | fail | pass | **(ก)** | Wikimedia (HAProxy) ตอบ scanner ของเราด้วย **HTTP 403** "Please respect our robot policy" เพราะ User-Agent ไม่มีช่องทางติดต่อตาม User-Agent policy ของ Wikimedia → เราตัดสิน headers จากหน้า error (ยืนยันแล้ว ดูหัวข้อถัดไป) | **แก้แล้ว** — User-Agent มี URL ของโปรเจกต์ |

## ข้อ 7 — wikipedia.org: ไล่หาสาเหตุ (20 ต.ค. 2026)

หลังเพิ่ม HTTP status + URL ปลายทางลง evidence (PR #11) ผลสแกนแสดง
`No Strict-Transport-Security header in response (HTTP 403 at https://wikipedia.org/)` จึงทดสอบทีละตัวแปรจากเครื่องเดียวกัน:

| Client | User-Agent | ผล |
| :-- | :-- | :-- |
| curl (HTTP/2 และ `--http1.1`) | `MFU-DomainSecurityChecker/0.1 (senior-project)` | 301 → ปกติ |
| Python urllib (OpenSSL เดียวกับ httpx) | เดิม | 200 → ปกติ |
| httpx | ค่าเริ่มต้น / เดิม / เดิม + `Accept: text/html` | 403 |
| httpx | เดิม + header แบบ urllib / SSL context ของ stdlib / ทั้งสองอย่าง | 403 |
| httpx | `MFU-DomainSecurityChecker/0.1 (+https://github.com/matthew69-dotcom/SEC_SCAN_FINAL_PROJECT) python-httpx` | **301 → ปกติ** |

ข้อความใน 403 (`server: HAProxy`): *"Please respect our robot policy https://w.wiki/4wJS when crawling us."*
สรุป: ระบบกัน bot ของ Wikimedia จัด httpx เป็น bot และกำหนดให้ bot ระบุช่องทางติดต่อใน User-Agent
→ แก้ให้ทุก request ขาออกของระบบ (headers, crt.sh, ip-api.com) ใช้ User-Agent เดียวกันที่มี URL ของโปรเจกต์
(`app/config.py: SCANNER_USER_AGENT`) — นอกจากแก้ผลแล้วยังสอดคล้องกับหลัก non-intrusive คือเคารพนโยบายของเว็บที่สแกน

บทเรียนสำหรับเล่ม: ถ้า evidence ไม่บันทึกว่า "ตัดสินจาก response ไหน" ความผิดพลาดแบบนี้มองไม่เห็นเลย
(คะแนน headers 0/25 ดูเหมือนเว็บตั้งค่าแย่ ทั้งที่จริงคือถูกบล็อก)

## ข้อค้นพบเพิ่มเติม (ไม่กระทบตัวเลขข้างบน)

1. **`mfu.ac.th` มี AAAA record = `::1` (loopback)** — SSL Labs ข้าม endpoint นี้ ("private address space")
   ตัวป้องกัน SSRF ของเรา (`netsafety.non_public_ips`) ตรวจแค่ **A record** ยังไม่ตรวจ AAAA
   ถ้าเครื่องที่สแกนใช้ IPv6 ได้ การ connect ด้วยชื่อโฮสต์อาจลองต่อ `::1` (เครื่องตัวเอง) ก่อน
   → **ช่องว่างจริงของ SSRF guard** ต้องตัดสินใจว่าจะแก้อย่างไร (ดูข้อเสนอใน PR) และควรใส่ในข้อจำกัด/ข้อค้นพบของเล่ม
2. `chula.ac.th` — IPv6 endpoint ติดต่อไม่ได้ (SSL Labs: "Unable to connect") ระบบเราใช้ IPv4 จึงไม่กระทบ
3. เกรดภาพรวมไม่ควรเทียบตรง ๆ กับ SSL Labs/securityheaders.com เพราะ rubric ต่างกัน
   (เช่น google.com: SSL Labs B เพราะยังเปิด TLS 1.0/1.1 — ระบบเราดูแค่โปรโตคอลที่ negotiate ได้)
   ให้เทียบระดับ check ตามตารางข้างบนเท่านั้น
